**Production is frozen at Build 280 unless deliberately promoted through the separate Production workflow. Development has intentionally diverged.**

Builds 281–290 established the modular registry, Packaging activation, owner-side read contracts, narrow Packaging bootstrap, Content artwork selection, active-runtime legacy GET retirement, write-response decoupling, and physical removal of broad Catalog/Inventory reads from the mature Packaging server source.

Build 291 moved the mature Packaging implementation into `functions/api/_lib/packagingDomainService.js`, and the native `/api/admin/packaging-write` endpoint began calling that shared write service directly. Build 292 retired direct POST authority at `/api/admin/packaging-studio`; authenticated direct legacy POSTs return HTTP 410 `packaging_legacy_post_retired` while the normal UI continues through `/api/admin/packaging-write`.

Build 293 extracted the proven Build 286 Packaging-owned read implementation into `functions/api/_lib/packagingReadService.js`. The native `/api/admin/packaging-bootstrap` endpoint is the active server read entry point and reports `read_service_build: 293`, `read_implementation_build: 286`, `read_authority: packaging-read-service`, and `shared_read_service: true`. Bulk Catalog and Inventory collections remain outside Packaging and continue through owner contracts.

Build 294 retires the remaining server-side GET compatibility authority at `/api/admin/packaging-studio`. It authenticates first; unauthenticated GET remains HTTP 401, and an authenticated direct GET returns HTTP 410 with `error_code: packaging_legacy_get_retired`, `build: 294`, `legacy_get_retired: true`, and replacement path `/api/admin/packaging-bootstrap`. The Build 292 POST retirement remains intact in the same route.

Development validation of Build 294 proved the direct 401/410 boundaries and active 293 -> 286 read provenance, but normal Packaging startup exposed a client race: the mature editor could issue its legacy-shaped GET before the dynamically imported modular runtime armed the read/write bridge stack.

Build 295 introduced `public/js/admin-packaging-startup-gate.js` to hold the mature editor's compatibility GET/POST until modular activation. It successfully prevented physical requests from reaching the retired server route, including during temporary degraded-auth startup. Live Development validation then exposed a deeper ownership flaw: Build 295 inferred the callable modular transport by reading the mutable `DDAuth.apiFetch` slot. The Build 286/288/289 bridge instances could report themselves armed while another wrapper still occupied that property. Build 295 therefore remains a historical safety step, but it did not achieve final live parity and is pinned at `afc50a80183ce30bc9c6182a4db3c4adc068f0ad`.

Build 296 removes that inference. Build 286 now exposes `transportBootstrapRequest()` over its already-created bootstrap bridge; Build 289 exposes `transport()` over its already-created write bridge; and the Build 290 facade exposes `transportLegacyRequest()` with `clientTransportBuild: 296` and `clientTransportReady`. The Build 296 browser adapter waits for that explicit facade and calls it directly. Normal compatibility GET is therefore routed explicitly through Build 286 to `/api/admin/packaging-bootstrap`, and compatibility POST explicitly through Build 289 to `/api/admin/packaging-write`, without inspecting current `DDAuth.apiFetch` ownership.

Build 296 preserves server/domain authority: read service Build 293 over proven read implementation Build 286; write gateway Build 292 over domain service Build 291; Build 294 GET tombstone; Build 292 POST tombstone. The mature `public/js/admin-packaging-studio.js` editor remains unchanged. Build 296 introduces no D1 migration, SQL/schema change, Wrangler/binding change, R2 enumeration, or Production change.
