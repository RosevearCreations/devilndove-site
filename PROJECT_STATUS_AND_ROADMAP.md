# Devil n Dove Project Status and Roadmap — Build 202

This is the primary business and release-readiness source. `AI_HANDOFF.md` contains deployment/operating rules. `MARKDOWN_INDEX.md` identifies specialist references. `docs/creative-asset-intelligence-platform/README.md` through `13_Media_Operations_Secure_Review.md` are the authoritative CAIP specification.

## Executive sanity check

Devil n Dove now has a governed content preparation and release loop:

```text
Approved finished product
→ Content Studio source-linked package
→ CAIP asset / rights / evidence / story record
→ metadata observation + immutable output plan + secure internal review
→ Release Board review draft
→ explicit public approval / publish gate
```

Build 202 closes the important gap between “we have a source archive” and “we are ready to risk an external render/publish provider.” It provides factual operational evidence and a safe internal preview path without pretending that a new image, thumbnail, video, derivative, post, or AI analysis already exists.

## What now works

1. Finished approved/published products create a Content Studio package while preserving original product images, videos, R2 records, gallery order, and featured media.
2. Content Studio prepares exact YouTube/Facebook/Reels/TikTok/website/GBP/SEO/blog/thumbnail/caption review plans.
3. Release Board prepares and governs Workshop Journal and website-gallery releases with factual copy, public-media, title/meta, slug, approval, publish/unpublish, and manual-performance gates.
4. CAIP creates canonical source references, preserves upstream rights restrictions, exposes transparent metadata scoring, and records evidence-backed editable/lockable story segments.
5. CAIP recommends source candidates for hero/gallery/thumbnail/short-video roles without treating those recommendations as public clearance or facts.
6. Build 202 records technical metadata observations and optional bound-R2 header evidence without fetching arbitrary URLs, reading media bodies, or modifying sources.
7. Build 202 creates immutable derivative recipes/plans for reviewable target outputs. It does not create a derivative file or call a provider.
8. Build 202 lets an administrator issue/revoke a short-lived, same-user, same-origin review proxy link for a bound R2 object. This supports safe internal review without making storage public.
9. Build 202 records secure-review grant activity and keeps provider registry/budget controls disabled and secret-free.
10. Desktop and mobile CAIP screens expose reachable operations controls, concise status, no-output honesty, and visual planning placeholders without creating CSS overflow/overlap.

## Business-model value

- Every finished piece can become a controlled set of reusable evidence, not a group of forgotten phone photos.
- We can decide which assets are suitable for a gallery, listing, story, thumbnail, social brief, or private review based on visible reasons and records rather than memory.
- A later rendering/publishing investment has a correct safety boundary: source consent, technical proof, immutable plan, cost cap, review, verified output, then release/publish.
- The same architecture can later support Devil n Dove custom work, process/teaching media, and Rosie Dazzlers detailing jobs without merging the businesses or weakening separate client consent rules.

## Search, public-content, and visual guardrails

- Keep one clear H1 on every public page. Build 202 keeps all public HTML one-H1 checked; CAIP admin remains `noindex,nofollow`.
- Publish helpful substantive content supported by actual source record/evidence and selected approved media. Do not generate thin pages just to add keywords.
- Keep titles, meta descriptions, captions, visible copy, alt text, structured data, and actual final media aligned.
- Use descriptive image alt text in context, not keyword stuffing. Final public assets need real crawlable URLs only after the Release Board approves them.
- Do not claim a video is available to Google/video search until public bytes, thumbnail, duration, and watch-page metadata genuinely exist.
- Preserve meaningful content/media on mobile and desktop. A compact mobile layout must not hide factual public content.

## Next implementation wave

1. **Live proof:** Deploy Build 202 and document a real test through probe/plan/review/revoke with no source changes.
2. **Source verification:** Add bounded source checksum capture and drift detection with costs, retry, and recovery planning.
3. **Technical extraction:** Add real duration/codec/frame information using a controlled, versioned, consent-aware provider or worker.
4. **Derivative worker:** Produce actual image/video derivatives only in a separate output namespace with output checksums, visual comparison, and manual approval.
5. **Retention/hold:** Add lifecycle/retention/legal-hold/recovery controls before any object cleanup automation.
6. **Render/export adapter:** Add signed input manifests, template/disclosure policies, cost budgets, retries, outcome verification, and manual fallback.
7. **Publishing adapters:** Add OAuth connections only after preview/confirm, account ownership, consent, delivery proof, failure recovery, and rollback controls are built.
8. **SEO publication:** Consider server-rendered/pre-generated Journal/Gallery story pages and sitemap expansion only after substantive released content and Search Console evidence support it.
