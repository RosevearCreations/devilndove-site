## Actual ownership and delivery steps
1. A verified, active authenticated Administrator opens the I.T. Privacy command centre. GET is read-only; no email is automatically sent by screen loading, production deployment or a scheduled worker.
2. Only after the currently signed-in Administrator checks an express consent checkbox and confirms one outbound test mail, a same-origin authenticated POST may send a one-time code **only to the registered email address on that same authenticated Admin identity**. Arbitrary supplied recipients and alternate contact addresses are ignored/rejected. Limit: two attempts per authenticated Admin over 24h.
3. A fresh cryptographically random 128-bit, uppercase 32-character hex code exists only in the outgoing Resend email and process memory. Source D1 stores an SHA-256 digest, a hashed recipient fingerprint, source timestamps and a SHA-256 digest of the Resend provider message identifier, never any original email, plaintext code, Resend API secret or full provider ID. The accepted provider API response is recorded separately. Failed or ambiguous sends are invalidated and marked HOLD, not declared delivered.
4. Only an explicitly posted 32-character code from the actual authenticated Admin's inbox can produce the independent original D1 `inbox_confirmed_at` receipt, within 15 minutes and at most five failures. The receipt is immutable; it cannot be cleared, deleted, duplicated, or reused. Wrong/expired/replayed codes fail closed and do not change any customer password. An independent original DB readback confirms the saved receipt.
5. A confirmed code demonstrates access to **that particular consenting Admin mailbox**. It is *not* provider's signed `email.delivered` webhook, nor proof of recovery-email delivery to ordinary customers, bounced/suppressed/open statuses, or end-to-end completion of an actual customer password reset. The Resend API `id` means provider acceptance; it is not recipient delivery. Genuine Resend `email.delivered` webhooks would require distinct properly verified configured delivery-event custody in a future authorized build.
6. The original Cloudflare Privacy Worker remains deployed but `DND730_AUTOMATION_ENABLED=false`; no automatic privacy withdrawal dispatch, Master receiver enrollment, remote erasure, plaintext decryption, encryption-key retirement or customer mail pilot is authorized by this build.
