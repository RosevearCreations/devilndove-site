# Build 629 — Independent original archive byte readback, signed go-live decision and Meta readiness certification

**Deployment GREEN is not a live Meta connection.** Build 629 adds **Admin section 50** to retrieve the *two original, already signed* external archive locations from an immutable Build 628 custody record, check their exact raw bytes against the entire original signed Build 627 packet, and register a **separately signed** original-owner readiness decision. A successful review certificate remains **READ-ONLY / NOT CONNECTED**. It never posts to Meta, changes OAuth tokens/scopes, activates publishing or converts a code release into external owner approval.

## Original owner-supervised steps

1. Open Devil n Dove **Admin → section 50**, choose **Read current original Meta archive and readiness status**. It reports whether the original issuer/witness/owner verification and the actual one-use Meta GET source are still current, whether the proposed Build 629 tables exist, and any previously recorded archive receipt. It does **not** fetch archives or invoke Meta automatically.
2. If signed source authority remains HOLD, return to **sections 44–49**. The original issuer, separate independent witness and owner must verify key fingerprints/pins, no quarantine, owner ledger, actual original Meta Page-ID GET outcome, separate signed acceptance, new short-lived 627 decision and the three-party 628 custody packet. Any expired window, missing genuine GET or changed page ID means **HOLD**. Do not reuse a spent provider nonce or extend an expired signature.
3. If the 629 source schema is absent, the authorized original D1 operator must separately approve and apply the **proposed migration 0064** after reviewing backups and the genuinely applied prior proposed **0052–0063** migrations. The canonical D1 migration gate remains unchanged: owner-controlled Development→Production approvals and source readback are required. **GitHub production GREEN does not apply proposed SQL or imply the real D1 tables exist.** [Proposed SQL 0064](../../migrations/proposed/0064_devilndove_build629_original_meta_archive_readback_go_live_hold.sql).
4. Copy the exact *saved* Build 628 `custody_sha256` into section 50. It must correspond to the original three-party signed custody and **two separately controlled, credential-free HTTPS archive URLs**. Both archives must actually serve the *identical compact JSON bytes* of the original signed Build 627 `payload` and three `signatures`: same encoding, order, whitespace and characters. Even harmless reformatting changes the byte identity. Obtain any necessary public, read-only archive access independently before testing. No private tokens, signed access query parameters or passwords are allowed in URLs.
5. With admin step-up and original owner supervision, click **Owner-supervised FETCH of TWO original external archives (HTTPS BYTE CHECK)**. This is the **only** Build 629 action that performs external requests. It sends at most **two GET requests** to the exact previously signed hostnames (no caller-selected URL), uses TLS/HTTPS, no cookies/credentials, no redirect following, a **16 KB** maximum per archive, a **six-second** timeout and direct byte-for-byte comparison to the signed original packet. Any HTTP error, redirect, private/internal hostname, wrong length, oversized stream, changed byte or expired original signer window fails closed; the application does not save a successful readback unless **both** match.
6. If both public archives match, the original server writes **one immutable readback receipt** to `dd629_original_meta_archive_readbacks` with the exact source custody hash, two HTTPS references, byte counts, content SHA-256 hashes and canonical readback digest. It does not store Meta tokens or downloaded content. A second attempt for the same custody is prevented by the unique constraint; a changed original packet requires a new original ceremony.
7. Click **Prepare UNSIGNED original go-live readiness review template** with admin password. This rechecks the exact stored byte receipt and current 627/628 source proof and returns a read-only decision template. **Unsigned is not approved.** The original `ISSUER`, separately authenticated `WITNESS` and `OWNER` independently inspect the exact source, external archive bytes, one-GET receipt and current permissions, then sign the *same* canonical 629 payload using their original securely held Ed25519 keys. The owner chooses either `CERTIFY_ORIGINAL_META_READ_ONLY_CHANNEL_READINESS_NO_ACTIVATION` or `HOLD_ORIGINAL_META_CHANNEL_READINESS` before signing. Neither signature option authorizes operational publishing. The decision expires within ten minutes and no later than both underlying signed 627 and 628 approvals.
8. Paste the three *public* original signatures and payload into section 50, enter admin step-up password and click **Record ORIGINAL independently SIGNED owner readiness decision — NO CONNECTION**. The server checks current source authority, original signer identities/keys/quarantine, exact signed 627+628 packets, immutable two-host HTTPS byte receipt, expiry and fresh original three-party signatures. It only **appends** the decision to `dd629_original_meta_go_live_decisions`. The SQL schema prevents UPDATE and DELETE.
9. Choose **Independently reverify SAVED owner readiness certificate — NO PROVIDER**. The application re-reads both immutable records, recomputes the archive receipt digest and original signed identities, and reports either `go_live_readiness_certified: true` for a current separately signed `CERTIFY` or `false` for `HOLD`, expiry or mismatched evidence. Even a true result always reports `connected: false`, `provider_channel_connected: false`, `publishing_enabled: false`, `provider_get_performed: false` and `activation_requires_separate_owner_control: true`. A **separate, new operational authorization** would be needed for any future actual Meta connection activation.
10. Retain original signed packets and external readback evidence in separately controlled owner archives. Recheck immediately before any later activation; past signed decisions are historical evidence, **not** perpetual permission or a background credential renewal. If source authority expires or changes, return to the original owner process and obtain fresh, non-replayed signatures.

### Trust boundaries, tests and release constraints

- `GET /api/admin/trust-archive-certification-629` is admin authenticated and `no-store`. Its readback is local D1 only.
- `POST` is same-origin JSON and **admin step-up** for all four explicit actions. Two of them write only new **append-only original evidence/decision records**; the other two are read-only. No DDL or proposed migrations run at request time.
- The URL reader accepts only the previously triple-signed original custody URLs, public DNS-style HTTPS hosts, no URL credentials or query strings, no redirects, a strict byte cap and short timeout. A remote archive can still be outside our control; independent custodian governance remains an owner responsibility.
- Original external proof remains **HOLD** until both authorized archives return real matching bytes and the *separate* owner decision exists. Never represent source fixtures, proposed SQL or a GREEN release pipeline as a real original Meta GET or authority signing ceremony.
- After the independently promoted QL-364 source-health change, runtime source measurement grows from 1,835 files / **18,365,765 bytes** to 1,837 files / **18,395,500 bytes**. The narrowly reviewed limit becomes **1,837 files / 18,396,000 bytes**, leaving only 500 bytes of headroom. All individual JS/CSS/HTML, inline URI, D1 authority and protected release checks remain intact.
